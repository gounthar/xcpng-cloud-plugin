The SHA-256 fingerprint of the certificate the Xen Orchestra appliance presents, as 32 hexadecimal pairs. Colons are optional and case does not matter, so a value pasted from openssl x509 -fingerprint -sha256 or from a browser's certificate viewer is accepted as-is.

Leave it empty if the appliance's certificate is signed by a certificate authority the controller's JVM already trusts. An appliance still on the certificate it generated for itself is not that case and needs its fingerprint pinned here.

To find it: leave this empty and press Test connection. If the certificate is not trusted, the result shows the fingerprint the appliance presented. Check it against the appliance itself, then paste it here and test again. Reading the fingerprint does not complete the connection: the certificate is inspected and refused, so no token is sent to a host that has not been confirmed.

Once pinned, only that exact certificate is accepted. If the appliance's certificate is replaced, connections fail until the new fingerprint is confirmed and saved here. That is deliberate: a replaced certificate is either an administrator's doing or an attack, and only a human can tell which.
