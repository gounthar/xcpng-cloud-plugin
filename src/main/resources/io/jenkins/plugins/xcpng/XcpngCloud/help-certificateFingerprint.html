The SHA-256 fingerprint of the certificate presented by whichever host Pool URL names, as 32 hexadecimal pairs. Under the XAPI backend that is the XCP-ng pool; under Xen Orchestra REST API it is the appliance. Colons are optional and case does not matter, so a value pasted from openssl x509 -fingerprint -sha256 or from a browser's certificate viewer is accepted as-is.

Leave it empty if the pool's certificate is signed by a certificate authority the controller's JVM already trusts. XCP-ng ships a self-signed certificate, so a stock pool is not that case and needs its fingerprint pinned here.

To find it: leave this empty and press Test connection. If the certificate is not trusted, the result shows the fingerprint the host presented. Check it against that host itself — on an XCP-ng pool, openssl x509 -in /etc/xensource/xapi-ssl.pem -noout -fingerprint -sha256 — then paste it here and test again. Reading the fingerprint does not complete the connection: the certificate is inspected and refused, so no credential is sent to a host that has not been confirmed.

Once pinned, only that exact certificate is accepted. If the pool's certificate is replaced, connections fail until the new fingerprint is confirmed and saved here. That is deliberate: a replaced certificate is either an administrator's doing or an attack, and only a human can tell which.
