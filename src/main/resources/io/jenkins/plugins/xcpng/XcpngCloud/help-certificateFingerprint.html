The SHA-256 fingerprint of the certificate this pool presents, as 32 hexadecimal pairs. Colons are optional and case does not matter, so a value pasted from openssl x509 -fingerprint -sha256 or from a browser's certificate viewer is accepted as-is.

Leave it empty if the pool's certificate is signed by a certificate authority the controller's JVM already trusts. XCP-ng ships a self-signed certificate, so a stock pool is not that case and needs its fingerprint pinned here.

To find it: leave this empty and press Test connection. If the certificate is not trusted, the result shows the fingerprint the pool presented. Check it against the pool itself — on the host, openssl x509 -in /etc/xensource/xapi-ssl.pem -noout -fingerprint -sha256 — then paste it here and test again. Reading the fingerprint does not complete the connection: the certificate is inspected and refused, so no credential is sent to a host that has not been confirmed.

Once pinned, only that exact certificate is accepted. If the pool's certificate is replaced, connections fail until the new fingerprint is confirmed and saved here. That is deliberate: a replaced certificate is either an administrator's doing or an attack, and only a human can tell which.
